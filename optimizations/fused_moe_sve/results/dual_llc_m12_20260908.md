# Two-LLC M12 background scaling on NUMA3

## Decision

Both independent sessions reach a read-throughput plateau near291GB/s for
this M12 workload when both LLCs supply background work. Balanced48/64/78
backgrounds produce approximately278/288/291GB/s, while foreground time
continues rising from~0.94ms to~1.68ms to~2.04ms. This is an observed workload
plateau, not a measured architectural maximum for every access pattern.

Placement remains important independently of nearly equal total traffic:
39 same-domain backgrounds give~0.76–0.77ms foreground time, versus~0.42ms
for39 other-domain backgrounds, both at~252GB/s. A single total-DDR-bandwidth
input cannot uniquely predict foreground time in this measured set. Do not
fit new parameters from this exploratory sweep.

## Scope and topology

Class E Lab experiment, no model fit or production change. Target
Arm-codex-internal reports NUMA3 CPUs240–319, LLC groups240–279 and280–319.
Foreground M1/1T W13 remains CPU304; controller CPU240. Background M12/1T
full-stripe kernels use independent8MiB B andfour copies, rotating after
each complete M12 call. Backgrounds use no cross-panel windowing.

Placements:

- Same LLC: counts8/16/24/32/39. CPU order288–303,280–287,305–319.
- Other LLC: counts8/16/24/32/39. CPU order241–279.
- Balanced: counts16/24/32/48/64/78, interleaving the two lists equally.
- Shared isolated baseline count0. Neither foreground nor controller CPU is
  used by a background worker. Actual start CPUs are recorded and checked.

The new optional protocol creates one foreground worker instead of16, freeing
otherwise reserved cores without time-sharing with the backgrounds. Before
each cell, CPU304 reads the full256MiB scrub buffer, then CPU240 reads the
same full buffer; both passes finish before background start. These changes
make this a NEW protocol regime. All placements have the same preparation;
isolated andsame16 are bridges to earlier results, not permission to pool raw
data with the old distributed-scrub/16-worker protocol.

Memory remains NUMA3 via numactl. About2.44GiB of background B is allocated
at the78-worker capacity for all cells, plus A/C/workspace/scrub. Ordinary
aligned memory under existing THP policy; no verified HugeTLB residency claim.
Foreground variants: real W13, B-only, AB-only, loaded4 no-store; no timestamps.
All W13 tasks have K4096/N1024, t=1, N16 backend tile,8MiB full owner stripe,
`window_tiles=0`/`full_n_team_stripes`,R13=1. W2 is not measured.

85 randomized cells per round,5 warmups +31 measured rounds, two independent
sessions, seeds269808/279808. Same allocations/workspace/four-copy rotation
within each process;5ms background lead-in. Verify all active M12 outputs,
inactive zero call counts, exact CPU placement andPMU running>=0.99.
No rate/plateau threshold is fitted; architectural peak is not inferred merely
from reaching the largest count.

## Bridge and interpretation limits

Isolated time (~302.5–302.7us) is close to the earlier~302–303us baseline,
but same16 now gives401/424us versus the prior384us. The new worker/scrub/
allocation regime is not interchangeable with the previous protocol, and
same16 also shows session variation. Use within-session paired comparisons;
do not pool these samples into old calibration or attribute all differences
to background count alone.

The experiment spans all78 available background CPUs in NUMA3 while reserving
one foreground andone controller. The two-LLC memory topology is covered,
but arrival remains5ms after startup, not uniformly sampled across phases.
The measured plateau applies to this M12 kernel,copy policy andcounter gate.
No claim is made that every CPU access pattern peaks at291GB/s. L3C ref
remains an unvalidated proxy and is retained without causal use.

For subsequent modeling, preserve at least total shared-memory load and
foreground-local LLC context as separate dimensions. The same/other matched
count pairs are holdout candidates, not new fit inputs authorized by this run.
