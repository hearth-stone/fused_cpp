# Per-channel W8A16 Plan V2 on AmazonM5192Cores

## Decision

Keep the additive API experimental pending model-quality validation and
cost-model selection. Two explicit implementations now exist. Register
dequantization converts B inside every GEMM K-loop. Cache dequantization
converts each searched Plan V2 B window once into thread-local BF16 scratch and
reuses the existing BF16 JIT kernel across M panels. The latter fixes the
captured long-route regression, but a full-stripe window can regress badly and
must not be treated as a valid cache policy by default.

The first table is the register-dequantized implementation. Cache-dequantized
window results are:

| Workload | W13/W2 window per thread | BF16 ms | W8 cache ms | Same-window speedup | Relative L2 |
| --- | --- | ---: | ---: | ---: | ---: |
| V4-Flash TP2 captured seq70/layer27 | 512 KiB / 256 KiB | 27.378 | 20.565 | 1.331x | 1.519% |
| V4-Flash TP2 uniform M48 | 256 KiB / 128 KiB | 24.228 | 18.295 | 1.324x | 1.519% |
| V4-Flash TP2 uniform M48 | full 4 MiB / 2 MiB stripe | 56.246 | 60.379 | 0.932x | 1.519% |

The V4-Pro run used clamped SwiGLU with limit 10, NUMA0 CPUs 0-95, five
warmups, 21 alternating runs, FP32 route storage, and
`profiles/m5-numa0-96c-quick-20260817.json`. Both formats consumed exactly the
same materialized Plan V2. M1 through M12 exact-M kernels also passed repeated
numerical checks; their relative L2 errors were 0.94%-1.28% on the small test.
The V4-Flash TP2 run used the same hardware profile with `mode=tp, degree=2`;
the balanced case selected strict 24 lanes x 4T. The captured route summary has
223 active experts, M1-M918, and route-count standard deviation 119.55; it
selected strict 6 lanes x 16T. Its top 16 counts are exact and its remaining
tail is deterministically reconstructed to match the captured moments. The
long experts amortize BF16 weight loads through cache reuse, while W8A16 still
pays conversion instructions for every K4, reversing the balanced-case gain.
Cache dequantization removes that repeated conversion for M>12. M<=12 has one
A panel and therefore stays on register dequantization. The 21-run captured
window sweep selected W13 8 tiles and W2 16 tiles (512 KiB and 256 KiB per
thread). Exact-M M1 through M12 checks produced 0.89%-1.28% relative L2 error.

## Follow-up

The planner should select register versus cache dequantization and supply a
nonzero stage window from the existing window calibration/search mechanism.
The current M5 profile has no production stage-window policy and resolves to
full stripe, so cache mode remains explicit. Model-level accuracy, additional
route distributions, SVE256, and a direct-BF16 W2 store remain required before
default adoption.

## Operator Integration

The optional public `fused_moe_tiled()` facade now selects BF16 or W8A16 from
the prepared-weight type. `fused_moe_w8a16_tiled()` obtains a Plan V2 from the
installed `MoePlannerRuntime`; it has no uncalibrated fallback. A native M5
NUMA0 integration check used E4, M24 per expert, H64/F32, and 96 threads. Both
register and cache W8A16 traversed the real planner/native SVE path and measured
1.067% and 1.133% relative L2 error versus BF16. The repeated planner lookup
was a cache hit with 62.3 microseconds reported planner overhead in the final
run.
