# Amazon C8i 2-core AMX W2 store/merge epilogue

Date: 2026-07-20

Machine: `AmazonC8i2Cores`, pinned to CPU 0 or CPUs 0-1. The extension was
built with GCC C++17, Xbyak, AVX-512 BF16, and AMX BF16. Weight packing and JIT
warm-up are outside timed regions. Python comparisons rotate all variants in
one process; the standalone W2 and merge benchmarks also rotate their variants.
Numbers are medians. CPU frequency and host thermal state were not fixed, so
small sub-percent differences are treated as noise.

## Variants

- `baseline`: `TILESTORED` one N32 result into a 2 KiB stack scratch, load each
  row into ZMM, calculate the flat-route address, and store FP32.
- `combined`: for M1N4/N64, store four accumulators into 4 KiB and calculate the
  route destination once per row. Other patterns retain baseline code.
- `tile_store`: assign expert-contiguous FP32 rows and issue `TILESTORED`
  directly to the route workspace. Merge translates flat route id to workspace
  row with a precomputed `int64_t` map.

All three are independent JIT cache keys. Top-k=1 `skip_weighted` cannot store
FP32 TMM state directly into a BF16 output, so `tile_store` intentionally uses
the `combined` converting epilogue there.

## Correctness

The targeted matrix covers M1N2, M2N2, M1N4, H/F tails, multi-expert top-k=2
routing, one and two workers, and direct BF16 top-k=1 output. The three modes
are bit-exact against `baseline`; the fused result remains within the existing
BF16 tolerance against the PyTorch definition.

```text
8 passed, 111 deselected
```

The final full x86 suite passed with `122 passed, 4 skipped`.

## Isolated W2 kernel

Command form:

```bash
OMP_NUM_THREADS=1 taskset -c 0 \
  benchmarks/bench_amx_bf16_w2_epilogues \
  M 512 4096 WARMUP RUNS baseline,combined,tile_store
```

| M | runs | baseline ms | combined ms | combined vs base | tile_store ms | tile_store vs base |
|---:|---:|---:|---:|---:|---:|---:|
| 16 | 101 | 0.180341 | 0.180454 | -0.1% | 0.157559 | +14.5% |
| 64 | 101 | 0.468053 | 0.468015 | +0.0% | 0.460025 | +1.7% |
| 256 | 81 | 2.159189 | 2.115424 | +2.1% | 2.111292 | +2.3% |
| 2048 | 31 | 18.512675 | 19.001596 | -2.6% | 18.324971 | +1.0% |

`tile_store` removes 663-1376 generated bytes in these exact-M kernels and is
consistently faster in this K=512 sweep. `combined` only changes M1N4 and its 4 KiB
scratch loses at M=2048, where the saved integer address work is not enough to
offset the larger scratch/store sequence.

### Store-dominated K=32 sweep

Reducing K from 512 to one K32 tile keeps the output size fixed while making
the epilogue/store path dominant. “Effective output GB/s” divides the logical
FP32 output bytes by total W2 time, so it includes the identical one-tile GEMM
cost and is a conservative store-throughput proxy.

| M | baseline ms / GB/s | combined ms / GB/s | combined speed | tile_store ms / GB/s | tile_store speed |
|---:|---:|---:|---:|---:|---:|
| 16 | 0.016951 / 15.46 | 0.017129 / 15.30 | -1.0% | 0.019128 / 13.70 | -11.4% |
| 256 | 0.284242 / 14.76 | 0.241195 / 17.39 | +17.8% | 0.335665 / 12.50 | -15.3% |
| 2048 | 2.342425 / 14.32 | 2.022901 / 16.59 | +15.8% | 2.875652 / 11.67 | -18.5% |

Direct TMM output is therefore not a raw store-bandwidth win on C8i. A
wide-stride `TILESTORED` is slower than a contiguous tile spill followed by
row-wise ZMM stores. At M1N4, removing the second address calculation is useful
when store work dominates; its 4 KiB scratch cost becomes visible again in the
K=512/large-M compute-and-cache regime.

## Merge-only cost

`bench_amx_bf16_merge` builds the same balanced expert grouping as the
executor, materializes equivalent flat and expert-contiguous workspaces, checks
bit equality, and alternates flat/mapped merge order.

| tokens / E / top-k | runs | flat ms | mapped ms | mapped latency delta | mismatches |
|---|---:|---:|---:|---:|---:|
| 32 / 8 / 2 | 101 | 0.025480 | 0.028482 | +11.8% | 0 |
| 256 / 8 / 2 | 101 | 0.348426 | 0.348411 | -0.0% | 0 |
| 1024 / 1 / 2 | 51 | 1.433618 | 1.442828 | +0.6% | 0 |

The extra map load matters for a tiny merge but disappears behind route-output
traffic once the workspace grows. This isolated result does not include the
cache state left by W2, which is why the end-to-end test remains authoritative.

## End-to-end fused expert

All cases use H=4096, F=512, top-k=2 and automatic AMX pattern/cache policy.
`M/expert` is the number of routed rows received by each expert. The benchmark
rotates `baseline,combined,tile_store` on identical data and packed weights.

| tokens / experts / M per expert | threads | runs | baseline ms | combined vs base | tile_store vs base |
|---|---:|---:|---:|---:|---:|
| 32 / 8 / 8 | 1 | 31 | 3.779841 | +0.1% | -0.1% |
| 32 / 8 / 8 | 2 | 31 | 1.953289 | +0.2% | +0.1% |
| 256 / 8 / 64 | 1 | 21 | 9.670225 | -0.2% | +0.7% |
| 256 / 8 / 64 | 2 | 21 | 4.572225 | +0.6% | +1.7% |
| 128 / 1 / 256 | 1 | 31 | 3.532668 | -1.0% | +1.2% |
| 128 / 1 / 256 | 2 | 31 | 4.700046 | +0.6% | -0.8% |
| 1024 / 1 / 2048 | 1 | 15 | 36.274721 | -0.6% | -4.5% |
| 1024 / 1 / 2048 | 2 | 15 | 33.702671 | -0.6% | -3.1% |

Positive deltas mean faster than baseline. The isolated W2 gain does not
translate uniformly: route-map setup, merge/cache interaction, and the direct
large-stride AMX stores change with M and thread scheduling. In particular,
`tile_store` wins the measured medium balanced two-core case but regresses the
large hot expert substantially.

## Decision

- Keep `baseline` as `auto`; its performance is the most stable across the
  current K, routing, and thread space.
- Retain `combined` and `tile_store` behind
  `FUSED_CPP_MOE_AMX_W2_EPILOGUE` for reproducible A/B tests and a later
  dimension-aware policy.
- Treat a block-major tile-store workspace plus a block-major merge loop as a
  possible follow-up, not part of this change: it changes merge locality and
  needs its own traffic model.
- Move the active P1 item to persistent scratch/workspace lifecycle cleanup.
