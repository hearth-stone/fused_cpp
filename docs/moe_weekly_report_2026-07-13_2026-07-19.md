## 2. 一页总结

过去一周的核心工作不是单独再优化一次 GEMM，而是同时推进了四个层次：

1. 减少显式 expert-team 路径的 barrier、临时矩阵、scatter 和 route merge 开销。
2. 把 packed-B 窗口、线程宽度和并发 expert 数目变成可以测量和解释的联合维度。
3. 将 planner 从纯二维采样表推进到公式、microkernel demand 和实测校正结合的模型。
4. 建立 x86 后端框架，并在独立分支完成 AVX-512 BF16 和 AMX BF16 JIT 原型。

最重要的生产结论如下：

| 项目 | 当前状态 | 主要结论 |
| --- | --- | --- |
| SVE 显式 expert-team barrier 消除 | scheduled/async 启用 | 96T、route=12 的单 expert 最多提升 7.8%-9.0%；normal 默认路径原本没有这两个 barrier |
| FP32 W2 direct-route store | `main` 默认启用 | 长 route 提升 14%-16%，短 route 基本中性；去掉 `down -> scatter` 物化 |
| SVE weighted route merge U1 | `main` 默认启用 | 实验 unroll 的 isolated 收益为 8%-18%，E2E 小于 1%；U1 主要价值是去掉线程内 FP32 accumulator 分配与流量 |
| BF16 direct-route store | opt-in | route=1536 相比 FP32 direct 提升 4.68%，但仍缺模型级精度验证 |
| async ready-token merge | 带门槛默认启用 | 已实现 605/2048 token 提前 merge，但当前 E2E 收益约 0.3%，低于噪声下界 |
| packed-B byte window | 实验接口 | 最优窗口约等于每个活跃 worker 1 MiB，但不能设成全局固定默认值 |
| split-K/Kc | kernel 已接入，production 默认 `Kc=K` | isolated cold-B 可提升 6%-13%，但 96 核饱和波次回退 1%-9.5%；split-K 保留为显式 candidate |
| vLLM staged schedule | baseline/实验 | 能补救错误的静态线程宽度，但不优于正确规划的 fixed-team schedule |
| x86 AVX-512/AMX | `claude-wip`，未合入 `main` | AVX-512 exact-M JIT 消除尾部断崖；AMX fused expert 相比 AVX-512 提升约 2.6x-3.7x |

## 3. ARM SVE fused expert 优化

### 3.1 消除显式 expert-team 路径的冗余 barrier

提交：`156a797`、`4335e1d`、`206bd56`。

scheduled/async 的显式 expert-team 实现包含两个独立优化：

- W13 会完整覆盖 packed intermediate，因此不再先清零 intermediate，也不再等待
  清零 barrier。
- W2 N-owner 线程直接 scatter 自己拥有的列，不再等待单独的 W2 后 barrier。

normal 入口必须分开看：默认 non-hierarchical 路径原本就没有这两个 team
barrier；opt-in hierarchical N-split 路径没有 intermediate-zero barrier，只有旧
W2-to-scatter barrier，因而只采用第二项优化。当前默认 direct-route store 又会
绕过独立 scatter，所以第二项主要覆盖 scatter fallback。

在 96T 单 expert 上，关闭 direct-route 以隔离旧 scatter 阶段后，scheduled/async
combined 版本的代表性收益为：

| 路径 | route=12 | route=2040 |
| --- | ---: | ---: |
| scheduled | 7.77% | 1.74% |
| async | 9.04% | 0.94% |

带 route-weight merge 的路径仍有 1.3%-7.1% 收益。正确性覆盖 dirty scratch
复用、所有 tail kernel、scheduled/async、FP32/BF16 输出和 NEON fallback。

结论：scheduled/async 的两个冗余 barrier 可以安全消除，短 route 和超宽线程团队
受益最大；normal hierarchical 只涉及 W2-to-scatter barrier，normal 默认路径没有
对应收益。长 route 由 GEMM 主体主导，收益会被稀释。

详细数据见
[expert barrier 报告](../optimizations/fused_moe_sve/results/expert_barriers_amazon_c5_192c_numa0_20260714.md)。

### 3.2 W2 直接写 route buffer

提交：`b0a1643`。

旧流程为：

```text
W2 FP32 contiguous down -> scatter route_out -> weighted merge
```

新流程为：

```text
W2 FP32 direct route_out -> weighted merge
```

M12/M8/M4/M2/M1 的 SVE epilogue 都支持直接 route store，normal、scheduled、
async 三条路径均已接通。8 个 expert、每 expert 12T 的结果为：

| route/expert | baseline | direct | E2E 变化 |
| ---: | ---: | ---: | ---: |
| 48 | 0.715 ms | 0.718 ms | 无可分辨收益 |
| 192 | 1.575 ms | 1.542 ms | +2.18% |
| 1536 | 9.410 ms | 8.125 ms | +15.82% |
| 2040 | 12.455 ms | 10.697 ms | +16.44% |

长 route 中，W2 irregular store 本身只慢 0.7%-1.2%，但省掉 1.33-1.95 ms
scatter，W2-output 阶段缩短约 40%-42%。route=48 的 saved copy 仍位于私有 L2，
绝对信号不到 1 us，无法覆盖 E2E 调度噪声。

结论：FP32 direct-route 是明确的长 route 优化，也消除了每 team 的 FP32 `down`
scratch；短 route 没有显著收益，但也没有被证明存在稳定回退，因此已默认开启并保留
环境变量 fallback。

详细数据见
[W2 direct-route 报告](../optimizations/fused_moe_sve/results/amazon_192c_w2_direct_route.md)。

### 3.3 BF16 direct route 与 FP32 merge

提交：`e3e5007`。

W2 可以直接把结果转换成 BF16 存入 route buffer，最终 TopK 合并时再扩展到 FP32，
所以 TopK=6 仍然是 6 路 FP32 累加，而不是 BF16 累加。route=1536 时：

```text
FP32 direct: 8.087 ms
BF16 direct: 7.726 ms
throughput:  +4.68%
```

收益几乎全部来自 route-merge 输入从 FP32 减半为 BF16；W2 critical worker
本身没有变快。相比 BF16 scatter，BF16 direct 还降低 6.25% 延迟，并把代表形状的
post-W2 逻辑 payload 从 384 MiB 降至 192 MiB。

结论：实现和算子级精度已通过，但仍缺真实模型 TopK=6 精度验证，因此保持 opt-in，
不替换默认 FP32 direct-route。

详细数据见
[BF16 direct-route 报告](../optimizations/fused_moe_sve/results/amazon_192c_w2_direct_bf16_route.md)。

### 3.4 SVE weighted route merge

提交：`8292661`。

TopK=2/4/6/8 使用编译期 tree specialization，其他 TopK 使用 runtime fallback。
U1/U2/U4 三个 hidden-axis unroll 均保留。TopK=6 isolated merge 中，FP32 最好
提升 14.4%，BF16 最好提升 18.0%；完整 fused MoE 中收益只有 0.2%-0.7%，因为
W13/W2 占据绝大部分时间。

U1 最终成为默认路径，主要原因是它不再为每个 worker 分配和清零
`H * sizeof(float)` accumulator。更大的 U2/U4 在 hot-buffer microbenchmark
更快，但冷 streaming、FP32 TopK=7/8 和高线程数下可能回退。非 temporal `STNT1H`
也没有稳定收益，已拒绝。固定 TopK tree 改变 FP32 加法结合顺序，因此任意输入不保证
和旧 sequential-FMA 路径 bitwise 一致，只保证落在现有 BF16 输出容差内。

结论：merge tree 是一个小 E2E 优化和重要的内存管理清理，不应把 isolated
kernel 的 10% 以上收益直接外推到 MoE E2E。

详细数据见
[route merge 报告](../optimizations/fused_moe_sve/results/amazon_192c_route_merge_tree.md)。

### 3.5 native `out=` 与 ready-token overlap

提交：`eb086b2`、`1284a6b`。

`out=` 现在直接传到 native operator，最终 store 写入调用方 tensor，不再先分配
native result 再由 Python `copy_`。实现补充了 contiguous、CPU、BF16、梯度、
内部 overlap 和输入/权重/路由 overlap 校验，并正确更新 tensor version counter。

ready-token merge 允许某个 token 的全部 TopK expert 完成后，在长 expert 尾部仍在
计算时提前合并。首个 per-route 原子计数版本产生 12,288 个竞争 RMW，回退 23.35%，
已拒绝。当前实现改为每 expert 一次 completion publication、每 ready token 一次
CAS 和批量入队。

受控 25%/75% 分布中有 605/2048 token 提前完成 merge，但三次 median 收益只有
0.23%-0.33%，低于约 1% 噪声下界。结论是“实现了无明显回退的 overlap”，还不能
声称有稳定 E2E 加速。当前只在负载比达到 1.25 时启用。

详细数据见
[ready-token merge 报告](../optimizations/fused_moe_sve/results/amazon_192c_async_ready_token_merge.md)。

### 3.6 configurable packed-B window

提交：`379e216`。

W13 和 W2 可以按显式 byte window 拆成更多 N range，从而把一个 expert 的瞬时
packed-B 工作集从固定 4 MiB 继续缩小。route=2040、96 核、TP4 F=512 的结果为：

| shape | legacy 4 MiB | 最优窗口 | 最优时间 | 相对收益 |
| --- | ---: | ---: | ---: | ---: |
| 24 expert x 4T | 30.555 ms | 4 MiB | 30.554 ms | 0% |
| 48 expert x 2T | 85.958 ms | 2 MiB | 61.717 ms | 28.2% |
| 96 expert x 1T | 311.614 ms | 1 MiB | 133.123 ms | 57.3% |

三个最优点都约等于每个 active worker 1 MiB packed B，符合 2 MiB 私有 L2 需要给
A、store、prefetch 和替换冲突留空间的现象。但对 24x4T 再缩小窗口只会增加 A
重扫和 range dispatch 开销。

结论：window size 必须和 team width、并发 expert 数、route 共同规划，不能设置
全局 1 MiB 或 2 MiB 默认值。它目前是实验性 kernel/planner 联合维度。

详细数据见
[weight window 报告](../optimizations/fused_moe_sve/results/amazon_192c_weight_windows.md)。

### 3.7 streaming-B prefetch 与 Kc/split-K

提交：`58b3e63`、`8b7b89b`。

单核 M12 cold-B 实验首先发现：W13 的 2 KiB L1 streaming prefetch 可稳定提升
约 9.99%，W2 的 L2 prefetch 只有 0.73%。进一步在 asm 中交换 K/N traversal，
并使用 Kchunk-major packed B，使 reusable A+B slice 留在 L1：

| 环境 | 结果 |
| --- | --- |
| 192 核机单核 isolated，Kc=800 | M12/M8/M4/M2/M1 提升约 6.2%-13.2% |
| 8 核机单核 isolated，Kc=568 | 多数 Mr 提升 0.6%-2.4%，M8 回退 1.48% |
| 8 核 2 expert x 4T | route=12/2040 提升 2.03%/3.52% |
| 192 核 NUMA0 24 expert x 4T | route=12/2040 回退 9.52%/1.25% |

PMU 表明 Kc=800 不减少 compulsory cold-B 流量，但 M12 L1 refill 约减半、IPC 从
4.10 提升至 4.63。高并发冷权重波次中，NUMA 内存流量已经接近饱和，A-side L1
收益被压缩，而每个非最终 K chunk 仍要读写 FP32 partial C，因此出现净回退。

结论：generic Kc kernel 和 pack layout 有保留价值，但 isolated 最优不能直接成为
production 默认。`8b7b89b` 已恢复默认 `Kc=K`，只有显式设置
`FUSED_CPP_MOE_SVE_KC` 或 `FUSED_CPP_MOE_SVE_KC_L1_PERMILLE` 才启用 split-K。

详细数据见
[production Kc 报告](../optimizations/fused_moe_sve/results/amazon_192c_8c_production_kc.md)、
[M12 K-block 报告](../optimizations/fused_moe_sve/results/amazon_192c_m12_kblock.md) 和
[small-M K-block 报告](../optimizations/fused_moe_sve/results/amazon_192c_msmall_kblock.md)。

## 4. fusion 价值与 cache/traffic 结论

### 4.1 建立严格同 kernel 的完全非融合 baseline

提交：`9306af7`。

实现了以下显式 pipeline，所有 GEMM 使用和 production fused path 相同的 SVE
BFMMLA 主体：

```text
extract -> packA1 -> W1 -> SiLU -> W3 -> multiply -> packA2 -> W2
```

和当前 fused pipeline 对比：

| route/expert | 完全非融合 | fused | latency reduction |
| ---: | ---: | ---: | ---: |
| 1020 | 8.831 ms | 8.479 ms | 3.98% |
| 2040 | 16.970 ms | 16.412 ms | 3.29% |
| 8160 | 67.785 ms | 63.968 ms | 5.63% |

fusion 的算术指令只减少约 0.44%，但 route=8160 时 LL read miss 减少 56.1%，
backend memory-stall cycles 减少 57.9%。受控 p99 改善从 route=2040 的 3.90%
增长到 route=8160 的 5.75%，CV 约减半。

结论：fusion 的主要价值不是提高 BFMMLA 吞吐，而是避免 materialized
`extract/packA/SiLU/multiply/packA2` 工作集扩大后产生 lower-cache refill、stall 和
尾延迟退化。上下文越长、route 越长，这个价值越明显。

详细数据见
[unfused baseline 报告](../optimizations/fused_moe_sve/results/amazon_192c_unfused_pipeline.md)。

### 4.2 单核 L2/L3 窗口

提交：`fd25370`。

单核、同一 packed B 在一个 GEMM 内重复扫描的 PMU 结果给出：

- 2 MiB 私有 L2 的 refill 拐点从 1.5-1.75 MiB 开始。
- 工程上稳健的 packed-B L2 上限约 1.5 MiB。
- 若要求至少约 80% repeated-B retention，应使用约 1.25 MiB。
- 96 MiB nominal L3 的稳健单核窗口约 64 MiB；72 MiB 仍在 5% 性能损失内，
  80 MiB 开始明显下降。
- THP 下 DTLB miss、page fault 和地址翻译不是 64-96 MiB 性能拐点的原因。

这些数值是特定 access pattern 的调度校准，不是硬件 cache 可用容量常数。

详细数据见
[single-core window 报告](../optimizations/fused_moe_sve/results/amazon_192c_single_core_weight_window.md)。

### 4.3 单 expert N-split 与多 expert 并发不是同一个问题

同一批实验表明：

- 单 expert N-split 不会把 aggregate B 容量乘以线程数，它把 B stripe 分散到各核
  私有 L2，但会增加 A lane 扫描和同步成本。
- 多 expert 并发会增加 unique B、expert 固定开销和输入流数量。
- 固定 aggregate B 也不能保证性能相同，因为 A replication、N tile/任务数和
  route 粒度仍不同。

对 16 MiB split stage、固定 96 worker 和固定总 route，`3x32T` 比 `1x96T`
吞吐高 38.3%。对 8 MiB W13 + 4 MiB W2 的 TP4 shape，64 worker 下 `8x8T`
比 `1x64T` 快 2.31x；96 worker 下 `6x16T` 和 `8x12T` 构成最优平台。若每个
expert 都有 route=2040，则 16-24 个并发 expert、每 expert 4-6T 是实测平台；
48x2T 和 96x1T 会因 B stripe 和 active working set 过大显著下降。

结论：planner 至少需要同时考虑 active B、每线程 B stripe、W13 输入/A 扫描、
N tile 数、route/M-panel 数和 expert 固定开销，不能只使用一个“总 B 大小”。

详细数据见
[thread/weight working-set 报告](../optimizations/fused_moe_sve/results/amazon_192c_thread_weight_working_set.md)。

### 4.4 固定 active B 时，短 expert 数量仍然重要

在 96 MiB active split-W13 stage、固定总 FLOP 和 96 worker 下，把长 expert
拆成更多短 expert：

- 只替换 25% 的 expert 时，即使短到 M=204，吞吐变化仍在 3.2% 内。
- 全部替换为 M=204 时，尽管 active B 不变，吞吐下降 24.6%。
- instruction 基本不变，但 L2 refill 增加约 120%，IPC 下降 21.7%。

原因是 B reuse panel 数从 `M/12` 降低，同时 unique weight turnover、kernel call
和 barrier 次数增加。dynamic queue 可以缓解尾部负载不均，但不能消除 packed-B
turnover。

结论：短 expert 可以作为长 expert 旁边的填充任务，但“相同 active B 就有相同
TFLOP/s”只在短 expert 占比较低时近似成立。

详细数据见
[fragmentation 报告](../optimizations/fused_moe_sve/results/amazon_192c_fixed_active_b_fragmentation.md)。

### 4.5 四个 M12 worker 被长 expert 干扰的根因

2026-07-19 的 PMU 实验已由 `50603a5` 记录。四个 M12 worker
和本地 23x4T 长 expert 同时运行时：

| 指标 | isolated | mixed | 变化 |
| --- | ---: | ---: | ---: |
| 短任务时间 | 69.60 ms | 98.27 ms | +41.19% |
| instructions | 114.932 B | 115.009 B | +0.067% |
| L2 refill count | 3.086084 B | 3.086220 B | +0.004% |
| effective L2-refill bandwidth | 94.53 GB/s | 67.10 GB/s | -29.01% |
| `stall_backend_mem` | 305.3 M | 924.2 M | +202.7% |

固定 refill 量的服务速率下降解释了 wall time 增加，频率、指令数和额外 refill
都不能解释。实验进一步分出两个成分：

1. 跨 NUMA 仍存在、随 concurrent private-cache data activity 增长的芯片级效应。
2. 同一 NUMA/L3 domain 内随核心距离变化的额外 topology-local refill service
   penalty，占原始新增延迟约 66%。

结论：这是“private L2 refill 得到的有效服务带宽下降”意义上的带宽争用，不等于
NUMA DRAM STREAM 已达到上限。由于没有 uncore PMU，不能进一步声称具体瓶颈是
某个 LLC bank、mesh link、home node 或 memory-controller queue。

详细数据见
[M12 refill contention 报告](../optimizations/fused_moe_sve/results/amazon_192c_short_refill_contention.md)。

## 5. planner 与 cost model 工作

### 5.1 数学问题正式化

提交：`c3b15d6`、`8534a60`，并持续同步
[`MATHEMATICAL_MODEL.md`](../cpu_moe_schedule_optimization/MATHEMATICAL_MODEL.md)。

本周完成了以下形式化工作：

- 把 MoE 调度定义为 256 expert route-task 问题族，决策包括线程宽度、lane
  assignment、执行顺序和 kernel policy。
- 将真实 isolated time `I_i(t)` 与 dynamic contention slowdown
  `D_i(Z)` 作为执行速率，而不是把 cache bytes 错当成绝对硬约束。
- 区分硬 CPU 核心约束、renewable resource、cache capacity pruning 和软带宽争用。
- 证明判定问题可由 `3-PARTITION` 归约得到强 NP-complete。
- 在 `I`、`D` 有限且为正时，证明有限候选域上的全局最小 makespan 必然取得。

结论：planner 不需要假设目标函数凸或连续，也不能依赖单一 greedy 指标证明全局
收敛；可以证明的是最优解存在，而 exact solver、近似算法和实测 regret 负责求解
质量。

### 5.2 `T_iso` 从二维表推进到公式加残差

提交：`f32a9d5`、`123a153`。

当前 schema-v2 支持：

```text
T_iso(R,t) = O(t) + C(R) * phi_usl(t) * k_phi(t)
```

8 核 SVE/M12 的 held-out route 验证中，公式 median absolute error 为 1.40%，
P90 为 5.31%，最大 6.70%。完整二维表在同 anchors 上更准，但公式只需要一个
route curve 和一个 thread correction curve。M1/M2/M4/M8 与前两个 M12 panel
仍保留实测 residual，否则 tiny-M 最大误差约 17%。

结论：公式适合减少采样维度，但不能无条件替换旧表。历史 profile 默认仍走 table；
只有新 profile 序列化 `iso_formula` 后才 opt-in。一次 EP2 trace 中公式改变 lane
shape 后，旧表重打分差约 3.9%，高于 2% planner regret 门槛。

详细数据见
[`T_iso` 验证](../cpu_moe_schedule_optimization/cost_model/T_ISO_FORMULA_VALIDATION.md)。

### 5.3 microkernel-aware GEMM shadow model

提交：`e89d983`、`2cf54bb`。

cost model 被拆成三层：

```text
algorithm work -> ISA/kernel mapper -> measured machine response
```

算法层只描述逻辑 FLOP 和 compulsory tensor bytes；SVE mapper 再加入
M12/M8/M4/M2、physical tail、N tile、BFMMLA/load 指令、A/B cache traffic 和
split-W13 range；机器 profile 提供 BFMMLA、L1/private/shared service rate 和
fixed cost。

在 192 核机器 NUMA0 的 32 核 slice 上，steady M12 bulk 的 held-out W13/W2 stage
误差均低于 1.7%。SiLU 只占 W13 的 3.3%-5.5%，占 W13+W2 的约 2.3%-3.7%。

结论：panel-linear 模型可以准确描述同 shape 的长 M12 bulk，但目前仍是 shadow
model。它没有证明能预测 unseen F/H、tiny-M、另一 ISA 或另一机器，不能替换 active
planner 表。

详细数据见
[GEMM ECM 验证](../cpu_moe_schedule_optimization/cost_model/GEMM_ECM_VALIDATION.md)。

### 5.4 owner-cache working-set 模型

提交：`e89d983`、`04cd922`。

split-W13 N-split 下，每个 worker 拥有 disjoint B stripe，因此第一个可复用容量
应按 aggregate owner-private L2 估计，而不是只看共享 LLC。96 核 V3、EP2 的独立
scan 给出 3-8 个 expert、48-128 MiB 的优选 band。公式选择 4 expert/64 MiB，
在 route=1020/2040 fused holdout 上 regret 为 0.33%/0.00%。第一个超过 owner
budget 的 160 MiB 点下降约 18%。

8 核 V1 交叉验证退化到 1 expert/4 MiB，route=1020/2040 regret 都是 0%。但
route=48 在 V3 上 regret 达 17.27%，说明短 route 仍必须使用 empirical contention
table。

结论：owner-private cache 是 long-route split-W13 的可解释第一容量边界，但不是
所有 route 和 mapping 的统一公式。

详细数据见
[working-set 模型验证](../cpu_moe_schedule_optimization/cost_model/WORKING_SET_MODEL_VALIDATION.md)。

### 5.5 64 核 TP2/EP2 planner 校准

本周收尾并验证了 2026-07-13 的 split/no-split schema-v2 profile、真实路由摘要、
uniform 和 hotspot 分布：

| 模式 | 最大实测 regret | selected-plan prediction error |
| --- | ---: | ---: |
| TP2/EP2 六个 case | 1.98% | -2.93% 至 +4.40% |

EP2 hotspot 的 +4.40% 高估已经定位：短 rank 在约 28.5 ms 完成后，长 rank 会从
dual-rank derate 恢复到 single-rank rate；旧模型却把双 rank derate 应用于长 rank
完整 DAG。该缺失的 rank-lifetime release 解释约 88% 的误差。W13 占 W13+W2 的
67.3%-67.8%，所以已有 2/3 + 1/3 stage split 是准确的，不是误差来源。

按给定 60 GB/s intra-pair、20 GB/s inter-pair 通信模型，uniform 的分析值为 TP2
43.458 ms、EP2 48.003 ms。但这不是实际 distributed runtime E2E，且未包含完整
route gather/scatter/combine，因此不能外推为 TP4 一定优于 EP4。

详细数据见
[policy model 验证](../cpu_moe_schedule_optimization/POLICY_MODEL_VALIDATION.md)。

### 5.6 192 核和双 NUMA cost profiles

提交：`f99a99f`、`745f221`、`d1f5ba6`。

完成了 TP4/TP2/EP4/EP2、split/no-split 的 96 核 profile，并修正 profiler：复用
预分配 native `out`，把 output allocation/first-touch 排除出 `I_i(t)` 和
`D_i(Z)`。旧 allocate-per-call 大 route profile 不再适合作为 GEMM contention
校准。

双 NUMA TP4/F512 的同步双 rank E64 profile 中，route=2040 最优为每 rank
`24x4T`，双 rank wall 91.54 ms，聚合 35.89 TFLOP/s。改为真实 256 expert
人口后，M=12 出现宽平台：

```text
24x4T: 9.042 ms
48x2T: 9.049 ms
96x1T: 9.094 ms
```

三者只差 0.6%，说明旧 E64 profile 的 `24x4T` 不能外推为 E256 M12 的唯一最优
调度。M=12 冷 B 单波实验得到 96 个 1T expert 的 effective packed-B rate 为
352.1 GB/s；达到峰值 50%/75%/90%/95% 分别需要 12/24/64/86 个并发线程。

结论：profile identity 必须包含 local expert population、NUMA/rank topology、
kernel policy 和 output-allocation 口径。双 rank wall 必须取逐轮 pairwise max，
不能平均两个 rank median。

## 6. 调度实验结论

### 6.1 elastic N-split

提交：`d1fe95b`。

动态线程版本支持在粗 phase 边界从较小 N-owner 集合扩到较大集合，同时保持每个
logical N lane 在一个 phase 内绑定同一 worker。固定宽 phase claim 相对静态 kernel
通常在约 2.5% 内，一次 resize 的代价约 20-148 us。

若每个 M epoch 都重新抢 lane 并 barrier，EP4 会回退 21%-30%，短 TP4 W2 会回退
71%。而且更多线程并不总是更快：TP4 split W13 的 static 64T 比 32T 慢 17.9%。

结论：动态扩缩只适合粗粒度 phase/tail，前面的主体应尽量静态；planner 只有在释放
出的线程能执行其他 expert 时才可能获得系统收益。

详细数据见
[elastic N-split 报告](../optimizations/fused_moe_sve/results/amazon_192c_numa0.md)。

### 6.2 vLLM-style staged baseline

提交：`71b5abc`。

实现了先全局调度全部 W13 N-range、stage barrier、再全局调度全部 W2 N-range 的
baseline，并严格复用当前 SVE GEMM 和 fused epilogue。

- 6 个长 expert、每个 M=2048 时，staged 比正确的 `6x16T` fixed-team 慢 13.1%。
- 256 个 M=48 expert 时，staged 比错误的 1T/2T/4T fixed schedule 快
  7%-102%，但比最佳 8T fixed schedule 慢 0.82%。

长 expert 的损失来自重复 gather/pack A 和全局 W13/W2 barrier 阻止某个 expert
提前进入 W2。短 expert 中 global queue 可以修复错误的静态线程选择。

结论：vLLM staged 是有价值的 baseline 和 work-stealing 对照，不是当前 planner
的替代品。

详细数据见
[vLLM staged 报告](../optimizations/fused_moe_sve/results/amazon_192c_vllm_staged_schedule.md)。

## 7. ISA 架构拆分与 x86 工作

### 7.1 MoE 后端按架构和 ISA 拆分

提交：`a64ab82`。

native MoE 被拆为独立 Python extension `fused_cpp._moe_C`，目录分为：

```text
csrc/moe/common
csrc/moe/arm/common
csrc/moe/arm/neon_bf16
csrc/moe/arm/sve_bf16
csrc/moe/x86/avx2
csrc/moe/x86/avx512_bf16
csrc/moe/x86/amx_bf16
```

AArch64 采用 fat extension：common/NEON 使用 BF16+i8mm baseline，SVE 单独编译，
运行时通过 HWCAP/HWCAP2 选择；`FUSED_CPP_MOE_SVE=0` 继续强制 NEON。packed
weights 保持 backend-specific，SVE 还校验运行时 vector length。x86 通过独立
backend descriptor 和 CPUID/XCR0 边界接入。

结论：本周完成的不只是目录移动，而是建立了 ARM NEON/SVE 和 x86 AVX/AMX
可以独立编译、pack、dispatch、fallback 的扩展框架。

详细说明见 [native MoE backend layout](../csrc/moe/README.md)。

### 7.2 AVX-512 BF16 fused expert

其他分支提交：`9329229`、`6a34b63`、`c9bfb94`，位于 `claude-wip`，未合入
`main`。

第一版 AVX-512 BF16 fused expert 使用 `VDPBF16PS`，支持 W13 SiLU/multiply、
W2、route store、merge、1/2T 和 tail。和限制为同 ISA 的 PyTorch/oneDNN staged
baseline 相比，完整 operator 提升约 1.17x-1.71x。M 为 12 的倍数时，单 GEMM
性能在 oneDNN AVX-512 的 -1.4% 至 +1.4% 内。

intrinsic fallback 对非 12 倍数总是计算 physical M16，导致 M1/M4/M8/M11/M13
只有 oneDNN 的 21%-59%。Xbyak exact-M JIT 生成 M1-M12 kernel，并组合 M12+tail：

| M | JIT / intrinsic | JIT / oneDNN |
| ---: | ---: | ---: |
| 1 | 4.77x | 1.02x |
| 4 | 4.05x | 0.90x |
| 8 | 2.27x | 0.98x |
| 11 | 1.72x | 1.03x |
| 12 | 0.99x | 1.00x |
| 13 | 2.26x | 0.96x |

JIT code generation 约 0.018-0.034 ms，按 key 缓存；`auto` 可在 Xbyak 缺失或
生成失败时逐调用回退 intrinsic。结论是 exact-M JIT 消除了尾部断崖，同时没有
破坏 exact M12 主路径。

### 7.3 AMX BF16 fused expert JIT

其他分支提交：`45109d1`，分支状态为 `claude-wip`，未合入 `main`。

AMX backend ID 102 显式启用，`auto` 仍选择 AVX-512 backend 101。Xbyak 生成
exact M1-M16 W13/W2，线程在执行 tile 指令前申请 Linux XTILEDATA 权限。

代表结果：

| workload | AMX / AVX-512 | AMX / staged oneDNN |
| --- | ---: | ---: |
| hot M12 1T | 2.75x | 2.14x |
| hot M48 1T | 3.66x | 1.52x |
| balanced 96 routes 2T | 3.32x | 2.80x |
| hot M48 N-split 2T | 3.68x | 2.00x |

单 GEMM M16 达 408 GFLOP/s，高于 oneDNN AMX 的约 347 GFLOP/s。初版 M17 会
运行 M16+M1 并重复读取完整 B，是明显断崖。`2M x 2N` tile pattern 在同一个 B
tile 上计算两个 M panel，相比默认 `1M x 2N` 在所有测试 route 上提升
27.0%-78.5%；`1M x 4N` 只有 -0.3% 至 +3.1%。当前仍保留 `m1n2` 默认，`m2n2`
是 M>=17 的领先候选。

测试还发现并修复 AMX padded intermediate stride 缺陷：W13 的 F16 padding 和
W2 的 K32 padding 不一致时可能跨行读取。修复后默认、`m2n2`、`m1n4` 各 72/72
测试通过，large-M/tail 30 个进程共 450/450 通过。

结论：x86 路径已从“预留目录”推进到可运行的 AVX-512/AMX fused expert，但它
仍位于独立分支；在合入 `main` 前还需要明确 AMX pattern dispatch、更多形状/核心
数验证和默认 backend 策略。

## 9. 本周形成的总体结论

1. **最直接的 production 收益在 W2 之后。** FP32 direct route 消除大块 scatter，
   长 route 可获得 14%-16% E2E 收益，比继续压缩 SiLU 更值得优先投入。
2. **fusion 的价值主要是 cache 和尾延迟稳定性。** 平均加速只有 3%-6%，但 LLC
   read miss、backend memory stall 和 p99 的改善随 route/工作集增长而扩大。
3. **工作集不能只用 aggregate B 一个数表示。** 至少还需要 per-worker B stripe、
   A replication、M-panel reuse、N tile、expert turnover 和 topology-local refill
   pressure。
4. **isolated kernel 最优不等于高并发 production 最优。** Kc/split-K 是最明确的
   反例：单核提升 6%-13%，饱和 96 核波次反而回退。
5. **短 expert 不需要 B reuse 容量，但仍消费 refill service。** 它们可以作为长
   expert 旁路填充任务，但长任务的 cache-data activity 会显著降低短任务 refill
   服务速率。
6. **动态线程应在粗 phase 或尾部使用。** 每个 M epoch 重分配 lane 会破坏 B
   affinity 和引入 barrier；正确静态 team 仍是主体计算的基线。
7. **cost model 应采用理论工作量、kernel mapping、机器实测响应三层结构。** 公式
   可以减少采样，但 short route、跨 NUMA 生命周期和新 kernel policy 仍需要实测
   residual 与 holdout regret 验证。
8. **x86 的主要机会是 ISA-specific compute 与 exact-M。** AVX-512 JIT 解决尾部，
   AMX 提供 2.6x-3.7x 主体加速；下一步重点是多核/多 socket 和 policy dispatch，
   而不是直接切换默认 backend。
